# sam：Simple answer me with html（纸张精简版）

你只写 **内容草稿**（扩展 Markdown）。`sam` CLI 负责布局与 STE。**不要手写 HTML/CSS/SVG。**

本 skill 是 [answer-me-with-html](https://github.com/QingYunA/answer-me-with-html) 的精简自用版：**强制 paper**、无工具栏/回复/标注/主题切换/视频。讲义与 iframe 优先用本 skill。

用用户的语言回复与写草稿。

**除非用户特意要求某模板，以后生成 sam 都严格执行下方强制规则（MUST 不可改回 SHOULD）。**

组件语法细节一律：`sam help <component>` / `sam list`。本文件只定 **选什么、写什么、不写什么**，不定完整语法。

---

## 1. 适用（是否出页）

| 场景 | 动作 |
|------|------|
| 关联概念 ≥3、流程/协议、对比权衡、层级、时间线 | **出页** |
| 闲聊、单句事实、用户只要纯文本 | **不出页** |
| 不确定 | 偏出页 |

CLI：

```bash
node "${CLAUDE_SKILL_DIR}/scripts/sam.mjs"
```

（变量未替换时，换成含本 SKILL.md 的目录绝对路径。）

## 2. 强制规划（阶段 A｜内部，不对读者可见）

**阶段 A 只在脑内/草稿注释外完成。禁止把规划理由、映射口令、Skill 条文写进读者可见正文。**

对每一板按顺序做完，再进入阶段 B 写正文：

1. **识别面板问题**——这一板要回答的子问题是什么？（一问一板）
2. **判断信息结构**——过程？多方消息？层级？时间？对比？真实配额？事实？
3. **必选组件**——按 §3 映射；触发 MUST 的必须出现，不得用 callout+kv 文字墙顶替
4. **图是否有信息价值**——按 §4：图须回答明确问题、体现主题独有机制；无则改用表/文字或不画
5. **规划位置**——哪一板放哪张图；若 ≥3 个独立确需可视化的问题 → 拆面板/拆页或增加图
6. **自检遗漏**——过程板有无 flow/sequence？该 tree/timeline 的有没有？有没有用 kv 冒充流程？有没有泄漏规划口令？

整页一次 heredoc 渲染：

````bash
node "${CLAUDE_SKILL_DIR}/scripts/sam.mjs" render - --no-open <<'SAM_EOF'
---
title: 标题
lang: zh
template: doc
---
## 面板标题
```flow
A -> B: 说明
```
SAM_EOF
````

读输出：`✓ <path>` 成功；`✗ L…` 按示例改后重跑（可 `--replace <path>`）。回复末行给页面路径。有 STE/代码警告时先改草稿。

### 面板数量（保留）

- **3–8 面板**：太少不够结构，太多难扫读。
- **一问一板**：标题是子问题或结论短语；不要把公式塞进面板标题。
- **先结论后展开**：重要结论可用 `callout`。
- **语言**：跟用户问题语言；可在 frontmatter 写 `lang:`。
- **STE**：默认 `style: 80`；`strict` 会阻断出页；介绍页可用 `style: off`。

## 3. 结构映射（MUST｜按信息结构，不靠标题碰运气）

**按真实信息结构判断，不按项目类型套模板，不因标题含「构建/发布/流程」就硬画。**

| 信息结构 | 组件 | 力度 |
|----------|------|------|
| 多系统 / 多角色 **消息交互、请求响应** | `sequence` | **MUST** |
| 有序过程 / 条件分支 / 状态转换 / 单角色步骤链 / 调用路径（且步骤真实、可区分） | `flow` | **MUST** |
| 父子 / 多层分类 / 目录 / 组成 | `tree` | **MUST** |
| 时间节点、阶段或版本演进为核心 | `timeline` | **MUST** |
| 多对象 **同一维度** 比较（功能/价格/取舍） | Markdown **对比表** | **优先** |
| **真实**数值 vs 限额/预算/阈值上限 | `limits` | 见 §4 |
| 句内易错术语、对照纠错（克制） | `annot` | 见下方 |
| 实体与关系（数据模型） | `er` | 形状匹配时用 |
| 纯元数据短键值（标题块、规格、属主） | `kv` | 可用 |
| 结论 / 注意 / 单一提醒 | 段落或 `callout` | 按需 |
| 简单事实一句能说清 | 文字 | 别硬画 |

### MUST 细则（不可打折）

- **sequence**：参与者之间有消息往返、请求/响应、多系统握手 → **必须** sequence；**禁止**只用段落或 callout+kv。
- **flow**：存在 **≥3 个真实、可区分** 的有序步骤、条件分支、状态机、或项目特有调用/转换路径 → **必须** flow（单角色清晰步骤）或 sequence（多方消息）。**触发看信息结构，不看标题是否含「构建/发布」。** 无复杂过程则不捏造步骤。
- **tree**：明确的父子层级、组织/目录/模块组成 → **必须** tree；不要用缩进列表冒充。
- **timeline**：时间先后或版本阶段是该板的主问题 → **必须** timeline。
- **禁止**用 `kv` / `callout` / 长段落 **代替** flow / sequence / tree / timeline。
- **禁止**为省 token 删掉上述强制机制或把 MUST 改回 SHOULD。

### 其它触发

**annot** — 同时满足才用（克制）：同一句里有易混术语或正误对照；标注 ≤3 处；整页 annot 块尽量 ≤2；不用于整段讲解。

**er** — 实体 + 关系（含基数）是该板主问题；否则用表或文字。

**kv** — 仅短键值元数据（标题、规格、属主、版本号）；**禁止**把步骤写成「步骤1: …」塞进 kv。

**callout** — 单条结论/警告/提示；**禁止**把多步流程拆成多个 callout 冒充图。

另有展示组件无 `ask`、无主题切换、无页内回传 Agent。

### 优先级与冲突

冲突时按此顺序（高 → 低）：

1. **内容准确与结构表达**（该用的图必须在，信息不错）
2. **触发条件对应的组件必须出现**（MUST 表）
3. **视觉克制默认**（能文字别硬画；一图一问题；不为多样性堆图）

数量与拆分：

- 默认一页突出 **1–2** 个可视化重点；对比表与 kv **不计入** 该上限。
- 若存在 **≥3 个独立、确需可视化** 的子问题：**允许**拆面板、拆页，或合理增加图。
- **数量上限不得成为省略必要图的借口。**
- 禁止用 callout+kv 偷懒替代流程可视化。
- 同类可视化少重复；不为「看起来丰富」而滥用图表。

## 4. 图表真实性与信息价值

### 4.1 limits 语义（读过组件语义再选用）

`limits` 渲染的是 **当前值 vs 上限** 的进度条（可标 unit；超限变红）。语法见 `sam help limits`。

**仅当同时满足时用 limits：**

1. 有 **真实、可核实** 的数值（来自文档、规格、配额、测量，或用户明确给出）
2. 存在明确的 **限额 / 预算 / 容量 / 阈值 / 上限**（「不得超过 N」「配额 N」「上限 N」）
3. 条形对比能帮助一眼判断是否接近或超过上限

**禁止：**

- 把主观评分、推荐指数、「适合度 10/10」写成 `value / max 10`（无量化限额）
- 无依据时编造分数或上限
- 用 limits 表达「强/弱/适合/不适合」这类定性判断（改用对比表或文字；若必须打分，须标明 **主观/量表**，且 **不要** 用 limits 组件——用表或段落）

无量化依据 → 表或文字。渲染器本身按数值画条；选错组件是内容错误，不是渲染成功。

### 4.2 强制可视化时的信息价值

当 §3 触发 MUST 图时，图还须满足：

1. **回答明确问题**——读者看完能回答该板标题所问
2. **体现主题独有机制**——节点/消息/层级是该项目特有的，不是万能套话
3. **禁止凑规则**——通用「安装 → 配置 → 运行」「写 → 构建 → 部署」若无项目特有分支/产物/角色，**不要**画；改写特有路径，或改为表/文字
4. **无复杂过程则不捏造**——不要为满足「≥3 步」虚构步骤

### 4.3 正例 / 反例

**正例**

- 「用户 → API → DB 的请求响应」→ `sequence`
- 「Office/PDF → MarkItDown.convert → 统一 Markdown → RAG」→ `flow`（特有转换链）
- 「anthropics/skills → skills/frontend-design → …」→ `tree`
- 「v1 → v2 → v3 演进」→ `timeline`
- 「三款产品功能对比」→ Markdown 表
- 「句长 13 / 上限 20 词」→ `limits`（真实配额）
- 「规格名 / 版本 / 属主」→ `kv`

**反例**

- 正文写「转换路径（过程≥3步）→必须 flow」再贴一张图 → **泄漏 + 错误**
- 多步发布只用 callout + kv 列「步骤」→ **错误**
- three.js「适合度 10/max10 分」用 limits → **语义错误**
- 空泛「安装 → 配置 → 运行」凑 MUST → **无信息价值**
- 因「已经有两张图」删掉必要 sequence → **错误**
- 为凑数给一句事实硬套 flow → **错误**

## 5. 读者正文规范（阶段 B｜唯一交给读者的内容）

阶段 B 只写读者需要的话：结论、机制、对比、用法、入口。**不要写你如何选组件。**

### 5.1 禁止指令泄漏（P0）

以下内容 **不得** 出现在读者可见正文、面板标题、callout、图注中（阶段 A 口语/自检除外）：

| 禁止模式（典型） | 说明 |
|------------------|------|
| 「必须 flow / 必须 sequence / →必须 …」 | 把内部 MUST 写进正文 |
| 「过程≥3步」「过程 ≥ 3 步」 | 触发条件口令 |
| 「根据 Skill」「按 Skill 要求」 | 元指令 |
| 「信息形状是…」「信息结构是…」 | 规划术语（讲解 sam 产品本身时除外，见下） |
| 「禁止只用文字/annot/callout 代替」 | 写作纪律口令 |
| 「limits 比架构图合适」等选型独白 | 把选型理由当正文 |

**合法例外：** 当页面主题 **就是在讲解 sam / 本 Skill / 组件规则** 时，可以说明「sam 要求过程用 flow」——那是在讲产品，不是在泄漏规划。普通项目介绍页（markitdown、Hugo、three.js…）**不适用**此例外。

交付前用仓库脚本自检（见 §6）；修掉误报前先确认是否命中合法例外。

### 5.2 去模板化（P1）

- **不要**强制「A·坐标 / B·机制 / C·比较 / D·用法」四段套路。
- 按主题自然组织：特有机制、可验证用法、真实取舍、入口链接。
- 项目介绍页：写清它做什么、关键路径/结构、和相邻工具怎么选、怎么上手；**不编造**星标、分数、步骤。
- 面板标题用读者能懂的问题或结论，不用「坐标」当空壳栏目名（除非该板真在讲坐标系）。

### 5.3 文风

- 先结论后展开；短句；少套话。
- 渲染成功 ≠ 内容合格：语法能过仍可能泄漏、limits 误用、图无信息。

## 6. 渲染与质检

### 6.1 草稿 frontmatter

```yaml
---
title: 标题
template: doc   # 或 sheet
lang: zh
style: 80       # off | 80 | strict
mode: auto      # auto | light | dark
---
```

`theme` 可写可不写，**一律 paper**。

iframe / 外置 CSS：

```bash
node "${CLAUDE_SKILL_DIR}/scripts/sam.mjs" css -o paper.css
node "${CLAUDE_SKILL_DIR}/scripts/sam.mjs" render draft.md -o page.html --css-href paper.css --no-open
```

### 6.2 发布前质量检查（未过则改稿重渲）

**自动（脚本）：**

- `npm run check` — USAGE / SKILL 结构 / kv CSS 等
- `npm run test:leakage` — 草稿/HTML 指令泄漏（含 Lab 反例）
- `npm run test:agent-cases` — 期望草稿可渲染（**非**真模型行为证明）
- `npm run test:kv` — kv 布局

**Agent 清单（语义，脚本兜不住）：**

| 项 | 问自己 |
|----|--------|
| 纯净度 | 有无规划口令/Skill 术语泄漏？ |
| 适配 | MUST 形状是否用了对应组件？有无 kv/callout 顶替？ |
| 真实性 | limits/数字/步骤是否有依据？有无编造分数？ |
| 信息密度 | 图是否回答该板问题？是否项目特有？ |
| 针对性 | 是否套用 A/B/C/D 空壳？对比是否具体？ |
| 布局 | 窄宽可读？kv 1–6？长 URL 未撑破？ |

未过 → 改草稿 → 重渲 → 再检。
